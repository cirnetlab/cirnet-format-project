## Performance

Unmodified release benchmark workloads were compiled once per source tree.
Timing runs were sequential on the same machine with the same NTFS scratch
parent. Default workloads ran baseline then candidate. The advanced workloads
ran candidate then baseline. Each used one warm-up and seven samples.
Throughput uses input bytes divided by mean time. Peak working set was the
largest process peak sampled at 40 ms intervals. Reported p95 with seven
samples is the maximum observed sample. Filesystem caching and host scheduling
can affect short saves, hard links and synchronization.

- Small used 20 documents and a 1 MiB asset. Medium used 200 and 16 MiB.
  Large used 1,000 and 96 MiB. Their ZIP sizes were 1,057,703, 16,860,307
  and 101,076,377 bytes in both runs.
- Advanced used 256 documents, 2,012 hard edges, two 1 MiB JSON payloads
  and two 8 MiB assets. Its ZIP size was 16,878,252 bytes.
- A focused release probe on a 205,907-byte manifest with 1,000 documents
  used 100 measured samples after 20 warm-ups. The original intermediate
  DOM and typed load took a median 1.829 ms, while direct typed load took
  0.840 ms on the same corpus. Whole strict manifest decode measured 3.129 ms
  in the baseline and 1.607 ms with the direct typed fast path. JSON
  preflight and graph checks still run. Invalid typed inputs keep the
  separate version-diagnostic path.
- Transaction planning reuses hard-dependency traversal and the previous
  document read when checking the initial revision. The manifest and
  affected-resource checks at publication are retained. Package publication
  adds ownership bookkeeping and a synced pending-import marker. This work
  enables cancellation retry and recovery diagnostics.

### Follow-up on slower samples

The initial medium verification and staging median rose from 346.754 ms
to 498.883 ms. A focused medium-only repeat used the same workload,
scratch storage and seven-sample method in baseline/candidate/candidate/
baseline order. Its medians were 291.823, 240.463, 157.890 and 180.502 ms.
The slowdown did not repeat. The verification path now keeps the inventory
already read during verification for use at publication. It adds no
per-member reads, hashes or syncs during verify and stage.

The large single-document save measured 7.752 ms versus 9.197 ms, with
p95 improving from 9.787 ms to 9.582 ms. The earlier baseline run measured
9.432 ms at the median, within the same range as the candidate. The single-file
path retains the same file and manifest revision checks and atomic replacement.

Advanced verified publication measured 158.926 ms versus 196.305 ms.
The added destination ownership checks and synced marker trade some
publication latency for clean cancellation rollback and explicit restart
diagnostics. The earlier baseline itself measured 217.255 ms. These data
do not isolate the cost of each filesystem operation. Archive sizes, copy
integrity checks and manifest-last publication were preserved.

## Operational limits

A validated read set protects explicitly selected resources for cooperating
writers. Direct external filesystem modification requires separate
isolation. Resource and manifest byte revisions are local and do not supply
authorization. Windows lacks the directory synchronization used on Unix.
A cancelled import can reuse a verified stage after a clean rollback. A
retained directory or an interrupted-process marker needs inspection before
reuse, with caller-established ownership for cleanup. The persisted 1.0
profiles and the prior [Foundation evidence](v0.1.0-verification.md) remain
applicable within their stated scope.
